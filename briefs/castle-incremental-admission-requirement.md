# Requirement sent upstream: incremental admission and replay facts in Castle

As of 2026-11-12, satisfied by Castle v0.4.0 (released 2026-11-12; the published tag's peeled commit is 6e1b40bbf48994c8e5d2791ee26f0d8f9220a879), and all six items are adopted in Biblios as described under [Adoption](#adoption-with-castle-v040). The requirement as sent, as of 2026-11-11, follows unchanged. This requirement asks for capabilities in Castle; it implements nothing and edits nothing in Castle. It describes the capability class, not any consumer. Biblios uses only Castle's published interfaces and adopts each capability in a later transition, after its release is published and independently verified; until then every cost below is recorded honestly and nothing here is claimed as solved.

## Why

Biblios keeps one indexing core whose ordinary work should amortize to the entries it directly affects. Today every Castle admission validates the whole namespace, so every Biblios read, fence and commit costs time proportional to the size of the shelf, and a batch of per-entry commits grows quadratically. On synthetic shelves, 60 entries did not finish bringing current in 300 seconds. A sampled stack from a concurrent diagnostic showed the admission path spending its time in whole-namespace validation (one sample, not a complete attribution).

The operator directed, on 2026-11-11, that Castle's normal operations should validate only the records they touch, with damage elsewhere detected when it is accessed or by a full diagnostic, rather than blocking unrelated work immediately. That direction is a requirement on Castle's own reviewed implementation: touched or detected corruption stays fail-closed, with no unproved caching, no loss of history and no weakening of security.

## Requested capabilities

1. **Admission validates only what it returns or writes.** On every ordinary path, including opening a handle, admission keeps its constant-cost integrity checks and validates only the records it returns or writes. Full-namespace validation remains available as an explicit diagnosis read.
2. **A cheap committed-revision probe**, so a caller can decide whether another writer committed since a known revision without a full admission.
3. **Targeted entry reads at a stated revision**, returning exactly the named records (with their ancestor chain where a path is needed), refusing when the stated revision is no longer current.
4. **Paginated changed-since discovery** over the existing changed-revision column, reporting changed and removed entry ids since a revision, so a caller never enumerates the namespace to find what changed.
5. **The live-file count** as a constant-cost fact, so a caller can report how many live entries it has not yet recorded without enumerating them.
6. **The primary entry of a committed operation.** A supported public read naming, for one committed operation, its primary entry. That one fact is all a replay needs, so nothing else is asked for. Castle's owner selected (2026-11-11, design only, not implemented or released) a targeted read, `namespace_operation_target(handle, operation_id)`, returning the same namespace, state, result, error code and next action as the operation status plus `primary_entry_id` for a committed operation only, leaving the existing status, result, stored rows and status command byte-unchanged; Biblios accepts that read or any equivalent supported surface with the same semantics. The primary entry comes from the operation's own stored request: the created entry for an entry creation; the request's entry for content replacement, relocation, metadata change and single-entry removal; the subtree root for subtree removal; the new root for a duplicate; none for folder import, snapshots, result expiry and excision; none for every state other than committed. With it, every field of a replayed curation result is available through public reads, so a caller can answer a retry of an operation committed before it kept its own record of the request, including after the paths it named have changed. A full historical request read is not needed and is not asked for.

## Adoption with Castle v0.4.0

As of 2026-11-12. Castle v0.4.0 publishes every requested capability: touched-record admission with full validation kept for the explicit `diagnose` read and the whole-sequence excision reads (item 1); the `probe` read with the revision, the database generation and the live-entry and live-file totals (items 2 and 5); `get-entry` and `resolve` at a stated revision, each validating the record and its ancestor chain (item 3); paged `changes-since` keyed to the database generation, reporting live and removed records (item 4); and `namespace_operation_target` (item 6).

Biblios adopts items 1 to 5 through its one core adapter and the shelf's own reads, using published reads only. The revision comes from the probe. A named entry is one `get-entry` plus its parent chain, each read pinned to the first read's revision, so one answer is one committed state. Discovery is paged change discovery after the observed revision; a different database generation (an excision cutover, or a store never observed) is resynchronized from revision zero with every recorded entry re-examined. Whole-tree work (the explicit sweep, the one-time preservation import, curation of a subtree, listing every file) reads every live record through the same paged change discovery, pinned to one revision, so even whole reads are validated record by record. Searching reads each hit's entry and parent chain, bounded by the hits. Measured on synthetic shelves of 20, 60 and 200 entries (counts, not time): bringing one new entry current costs the same number of Castle record validations and admissions at every size, a call with nothing to do validates no record, a one-hit search costs the same at every size, and none of them reads the whole namespace. Item 6 is adopted for the shelf's curation replay: a retry of an operation committed before Biblios kept its own record of the request takes the operation's entry from `namespace_operation_target`, so a subtree removal or a duplicate replays with its exact root after its paths changed, and nothing is executed again; an operation with no such entry still refuses explicitly. A recorded request is still re-issued verbatim, so Castle's fingerprint check answers it.

**Threat model under touched-record validation.** Castle now validates only the records an operation returns or writes. Damage in a record that is never touched is found when it is touched, by a whole-sequence operation, or by Castle's explicit diagnosis; it no longer blocks unrelated work at open. Biblios's reads stay fail-closed on every record they use, because each was validated as it was read; Biblios does not assume that opening a shelf validated the whole namespace, and claims no detection of deliberate tampering in records it has not read. A full check of the namespace is Castle's explicit diagnosis, not a side effect of ordinary use.

**Existing shelves.** Castle v0.4.0 stores namespaces in format v2. A shelf written with Castle 0.3 is refused at open with Biblios's typed `NamespaceFormatError` (and the consumer code `namespace-format-unsupported`), naming Castle's explicit migration `castle.namespace_migrate_v1.migrate_namespace_v1(namespace_root, cas_root, session, backup)`. The operator runs that migration once, with a backup; Biblios never migrates and never alters the store.

## How Biblios proceeded until adoption

Until v0.4.0, Biblios's indexing core used only published calls: handle information, one entries snapshot per batch for discovery and changed-since, and `namespace_operation`. It recorded the resulting cost per call and per entry, made no claim that whole-namespace admission was solved, and adopted items 1 to 5 through one adapter once they were released. For curation replay, Biblios records the exact request it sends for every new curation call and re-issues it, so Castle's own fingerprint check answers the retry. For an operation committed before that record existed, a replay is exact from the public result for every kind except subtree removal and duplicate; for those two it refuses explicitly rather than guess, and exact replay of them is a final-release obligation on item 6, adopted through the supported targeted read once it is released and independently verified.
