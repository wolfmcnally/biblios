# Consumer adoption contract

This guide describes the experimental 0.7.1 library interface. The interface composes the existing Castle namespace, Palace index and Drawbridge conversion capabilities; it provides no authentication, authorization, encryption, sandbox or external publication protocol. Keep those responsibilities in the surrounding application. No new CLI or MCP operation is introduced.

## Bind existing storage

Use `ShelfBinding` to declare one absolute domain root and five nonoverlapping roots within it: namespace, active Castle store, Markdown mirrors, Palace state and scratch. Bind the shelf ID, namespace ID and complete active Castle identity, including its epoch and generation. The active Castle root may be an explicitly supplied successor inside that domain. Do not point a binding at a retired predecessor or let another actor change ancestor directories, mounts or symlinks during its lifetime.

`bind_shelf(binding, handle)` admits precisely the supplied Castle `NamespaceHandle`; it never opens a second coordinator. Set ownership to `borrowed` when the caller retains that handle, or `owned` when Biblios must close it on successful close and refused admission. `open_bound_shelf(binding, session)` opens one owned existing handle through the supplied Castle `AuthorizedSession`. It does not initialize missing storage, recover a pending operation or fall back to an older store. Initialization remains a separate explicit `init_shelf` operation; callers needing protected initialization supply the supported Castle environment themselves before binding.

A bound lifetime checks actual roots, handle access, manifest, namespace and active storage identity. Only Palace's local SQLite vector backend is admitted in this lane. Injecting a model alone does not constrain Palace's separate vector backend. Missing, corrupt, retired or unfinished storage refuses; it is not treated as an empty replacement shelf.

`access="read-only"` is independent of the shelf's sealed state. To prepare a dynamic shelf for a read-only mount, finish required derivation and call the writer's `checkpoint()`, then close all writers and readers. The checkpoint verifies mirror/index membership and records the exact rollback-journal database digest. Read-only opening requires that checkpoint for an existing index and creates no namespace lock or SQLite WAL/shared-memory sidecar. Requested mutations refuse before effects. This is not a seal or a promise that an unsupported filesystem preserves Castle's protection modes; qualify the actual destination.

`close()` is idempotent and closes only owned resources. `active_work` counts supplied callbacks still in flight; closing during provider work refuses with `work-active`. Wait for the original call to finish and for the count to reach zero before unmounting. Biblios does not close caller-owned embedding or reranking providers.

## Curate and retry

A `CurationRequest` contains the caller's UUIDv4 operation ID, expected namespace revision and one typed action. Keep the complete original request until its outcome is known. Actions cover file/directory creation, replacement, metadata updates, relocation, logical deletion, snapshots, creation-only folder import and no-content subtree duplication. Imports can reserve parent and child IDs together, including empty directories. They are not arbitrary mixed create/replace/move/delete batches.

Biblios serializes through the supplied namespace coordinator and refuses a new stale request before staging content. Castle binds the canonical operation kind, exact content addresses and sizes, metadata, targets, names, IDs and relevant option presence. An exact completed replay returns the original durable result and IDs, even after later namespace mutations. Reusing its operation ID with a changed request refuses; generating a new ID is a new operation, not recovery. `operation(operation_id)` reports the actual durable Castle status, with `unknown` meaning absent rather than successful.

Pass composed settings to `bound.curate(request, settings=settings)` to apply `biblios.max_file_bytes` to create, replace, import and copy admission. Omitting settings uses the default of 100 MiB (104857600 bytes) per source file. The setting must be a positive integer byte count. Import/copy aggregate payload is bounded by the larger of 64 MiB and that per-file allowance, so one permitted file fits. The remaining envelope is 100 files, 100 folders and 255 UTF-8 bytes per normalized name, subject to Castle validity and namespace capacity. Supply the intended settings on each call, including retries; the allowance is caller configuration, not stored shelf policy. It does not change the original request or authorize retrying an uncertain external operation. Castle's separate 16 MiB canonical metadata-request limit also applies. Copy plans freeze source/destination IDs and reuse the underlying content objects; independent destination entries do not depend on the donor entry continuing to exist.

After interruption, retain actual residue and the original operation. A reader does not repair it. The owning coordinator uses Castle's public `recover_namespace` with the original namespace/store/session, then explicitly opens the recovered binding and replays the original request. Recovery is a local durability boundary, not an assertion about an external client acknowledgment.

## Supply conversion and model providers

`ConversionRequest` passes exact original bytes, declared media type and an explicit operation scratch directory to the injected converter; it carries no name, because Castle's namespace is the only authority for names and paths and a mirror carries neither. It returns a typed converted or unconverted `ConversionResult` with converter/version provenance. `ConversionConfigurationError` reports a fixed safe configuration refusal; unsupported, document-failed and deferred document outcomes remain distinct. Original downloads are unaffected. Biblios never implicitly starts a converter, OCR engine or model service in this lane.

The renderer is `renderer(result) -> MirrorDocument(markdown)`: document content only, with no name. `render_escaped` is an explicit optional policy that quotes source structure while preserving its text. It is not imposed on existing mirrors. The index adds the entry's current Castle filename after the mirror's bytes as its own final section, headed `Filename`, so a rename re-embeds only that row and never touches the mirror. A mirror's front-matter header is never an authority: values under Castle-controlled keys (`name`, `filename`, `path`, `media_type`, `tags`, `dates`, `content_hash`, `content_address`, `cas_id`, `byte_size`, `size`) are ignored, and the other top-level scalar or list fields, except those `DerivationPolicy.provenance_header_fields` declares as converter provenance, are indexed before the filename as an attributed section headed `Mirror metadata`, one `key: value` line each. Keys are a letter followed by letters, digits, `_`, `.` or `-`, compared case-insensitively against the reserved sets; dates are written in ISO form. A header that is not a YAML mapping contributes nothing. Front matter is recognised exactly as Palace recognises it (`---` and LF line ends); a header that cannot be loaded at all, such as one with an impossible date, contributes nothing and the body still indexes (Palace v0.5.1). A `DerivationPolicy` names the converter, rendering, embedding convention/implementation, chunker and filename policy; equal vector dimensions alone establish no compatibility. Body and mirror bounds are explicit; malformed UTF-8 and oversized callback results refuse without truncation.

Conversion checkpoints bind the active namespace/store/epoch, entry/source identity, media type and policy to the caller's operation ID. Completed results replay without invoking completed callbacks. If a callback was dispatched but no durable result was recorded, status is uncertain: an automatic retry is forbidden. The consumer must reconcile that external outcome and explicitly opt into retrying it. This provides neither exactly-once remote execution nor a billing guarantee. Scratch and content-bearing checkpoints stay in the declared domain; supplied Python callbacks remain responsible for their own I/O.

### Declare finite conversion and storage envelopes

Source-upload limits are independent of conversion expansion. `DerivationPolicy` defaults remain 4 MiB for `max_body_bytes`, 8 MiB for `max_mirror_bytes` and 16,384 for `max_chunks`. Body and mirror declarations may be positive integers up to 512 MiB each; this is an admission ceiling, not a promise that both fit together. The complete conversion or derived checkpoint must fit within 512 MiB of serialized UTF-8 JSON, including JSON escaping, duplicated fields and every vector component. Reads enforce the same encoded boundary before parsing, and an oversized write leaves the previous durable checkpoint intact. It reports `checkpoint-write-failed` with recovery required; completed external effects are not undone.

`ConsumerPipeline(max_snapshot_bytes=64 * 1024 * 1024)` separately bounds the complete Palace snapshot's encoded database payload. A consumer may explicitly declare a larger positive finite byte budget, for example `128 * 1024 * 1024`, while retaining its existing body, mirror and row declarations. The same snapshot budget applies to donor reads, destination/replay reads, transactional publication admission and committed readback. It is a resource allowance outside semantic policy identity; changing body, mirror or chunk policy under an original operation ID remains a changed request.

These limits measure different representations. Palace snapshots count the documented database payload; checkpoints encode dense vectors as JSON numbers and can reach their ceiling first. Neither bound is an RSS limit. A bounded save encodes the complete document once before replacement, so the document and serialized text coexist in memory. Publication admission measures staged database state before COMMIT; it does not promise a pre-embedding size estimate or refund completed provider work.

A snapshot refusal uses conservative recovery diagnostics: derivation reports `derivation-failed`/`recovery-required`, and donor capture reports `read-failed`. Palace uses a general index error for budgets as well as integrity failures; callers must inspect durable status and reconcile actual state rather than classify exception text. After a successful precommit rollback, a `vectors-ready` record can finish the same original operation with an adequate snapshot budget without repeating completed conversion or embedding. The rendered mirror can already exist while no destination rows are committed. A failure during mandatory readback after COMMIT remains committed but unaccepted, and a failed rollback or I/O failure cannot be assumed effect-free. Preserve the original operation and uncertainty records; resource changes never authorize replaying an unresolved external dispatch.

## Derive independent destination rows

Create `ConsumerPipeline` with an explicit converter, renderer, `input_view`, `DerivationPolicy` and document embedder. The selector's Palace representation must equal `pipeline.representation` before indexing begins. Declare it explicitly for an empty index using Palace's supported selector API; an incompatible existing index refuses and requires a deliberate derived-state rebuild. Biblios does not relabel old breadcrumb vectors. `literal_inputs` is an optional explicit input view that submits each exact chunk body, including its Markdown heading, without a destination path prefix. Query embedding remains a separately supplied provider.

Call `bound.derive(pipeline, entry_id, operation_id=original_id)` to persist conversion, bounded model results and the actual atomic Palace publication. `bound.status()` reports recorded local work without dispatch, and `entry_status(bound, entry_id)` one entry's record, pending stage and mark. A completed operation replays only while its actual destination mirror and committed vector view still match. Completed observations retain their original storage/revision view and are labeled on replay. Cancellation cannot undo an external dispatch or a committed index.

Mirrors are user-owned. `derive` converts only new source data, a replaced file (a new ingestion) or a copy named by `copied_by`, the committed duplicate operation that created it; one copy receipt authorizes one first mirror, and copies made without a recorded intent refuse `materialize-evidence-unavailable`. A converted entry whose mirror exists is re-indexed from the mirror's current bytes and never rewritten. To rebuild a lost derived store while the mirrors survive, bind the shelf again, run one `bring_current` (the preservation import), then for each entry call `bound.grant_first_ingestion(entry_id, expected_cas_id=..., operation_id=..., expected_mirror_sha256=...)` with the digest of the mirror bytes you last accepted: the existing file is adopted as the entry's mirror only if its bytes hash to exactly that digest (otherwise `mirror-user-owned`; an absent file `mirror-missing`), and the next `bring_current` naming the entry indexes those bytes without converting or writing anything. A mirror edited between the grant and that call is isolated, never adopted; vouch again with the new digest to adopt the edit. An adopted mirror is user content like any other, and a later excision of its source keeps the file in place and reports it as kept rather than deleting it. `bound.update_mirror(pipeline, entry_id, operation_id=..., markdown=..., expected_sha256=...)` is the supported edit seam: it validates before writing (`mirror-update-invalid:<class>`) and refuses `mirror-changed-concurrently` when the file is no longer the bytes the caller saw. Every write that displaces or retires a mirror uses an atomic exchange or no-replace rename (macOS `renamex_np`, Linux `renameat2`; other platforms refuse `mirror-write-unsupported`) and keeps the displaced bytes as `<entry>.md.retained-<UTC>-<n>-<sha256>` with a provenance record under the Palace root naming the source and mirror digest Biblios had recorded, the reason, operation and revision; unknown fields are null, never inferred. Only explicit excision removes retained files and their records; whether replaced source bytes are kept or excised is not decided by Biblios. `status()` reports each entry's mirror state (`searchable`, `pending-reindex`, `pending-conversion`, or an isolated class: `mirror-missing`, `mirror-unicode-invalid`, `mirror-too-large`, `mirror-path-unsafe`) with retained and unattributed counts. An isolated mirror withholds only its own entry from search, `finish` and `checkpoint`; it never blocks the shelf. Seal refuses while any mirror is isolated. Retrying a replacement's original operation after `mirror-changed-concurrently` treats the intervening edit as the version being replaced: it is retained, not lost, and the new conversion is published; use a fresh operation after first deciding what to keep if that is not wanted.

After deriving a donor, capture `pipeline.donor(bound, entry_id, operation_id=donor_operation_id)` and nominate that finite `ReuseDonor` for a destination derivation. Only same-shelf live source identity, current converted mirror, complete representation, exact ordered embedding-input digests and the captured committed view qualify. Missing or ineligible donors take the ordinary path; malformed or stale binding/integrity evidence refuses. `reuse_converted_body=True` additionally declares that this converter/policy permits reuse of a donor's converted body; a converter never receives a name, so the body cannot depend on one. Compatible body vectors may still be reused after ordinary conversion when their exact inputs agree.

Document embedding and its progress callback release the namespace coordinator's mutex while retaining the same Palace writer admission. Ordinary public reads and strict search can observe the last admitted lagging view during that window; an existing admitted mirror stays intact even after its source is replaced. Current-hit checks still suppress obsolete content. Namespace changes during embedding refuse stale results, and the complete admitted derived view is checked before publication. Conversion, rendering and input-view preparation remain serialized. Supported competing writers wait outside the reader mutex; an admission timeout reports `writer-busy` with no operation effect. Failures after admission retain their actual uncertainty or recovery diagnostics.

Provider throttling is typed by Palace and classified once per entry by Biblios, after every slice the entry submitted has returned, so the result never depends on completion order. An entry is `pending` with effect `none` only when every failure of its provider calls left nothing performed (Palace's merged `delivery` is `not-sent` or `rejected`) and was a throttle, a deadline, a cancellation or a pacer refusal; anything else, including any slice whose delivery is `unknown` or `processed`, is `uncertain`. The code is `provider-throttled` whenever any attempt was throttled, whatever the certainty. Only Palace's `ProviderCallError` is classified; any other exception the embedder raises, including one shaped like a Biblios `ConsumerError`, is `callback-failed` and uncertain. Once any submitted call has been throttled, `bring_current` admits no further entry and sends no further slice: submitted calls drain, an entry whose slices were all answered still commits, an admitted entry left incomplete is `pending`/`provider-throttled`, and unreached entries stay marked; a serial call visits no further entry. `BringCurrentResult.throttled` is computed from the recorded entry codes, so a replay keeps it. `BringCurrentResult.local` (`CallLocal`) is never recorded and is `None` on a replay: `retry_after` (the longest provider hint still to wait, in seconds, when the call returned), `invocations_failed`, `answers_discarded`, `inputs_discarded`, and `usage`, Palace's summary of the call's physical attempts, retries included (`None` when the embedder recorded none). `provider_calls` counts embed invocations that returned, when each returns. Requeue a `pending`/`provider-throttled` record after `local.retry_after` under a new operation id without charging your failure retry; charge `uncertain` as before. Each pooled provider call runs in its own copy of the caller's context, and `bring_current` and search open Palace's `call_scope` from their `CallControl`, so Palace stops pacer waits, backoff and further attempts at the deadline or on cancellation; within a request Palace lowers each transport timeout to the time remaining, which is not a total-request bound (a response that keeps arriving in pieces can outlast it, and SDK credential resolution is not bounded), and Biblios drains every submitted call before returning, so there is no guaranteed total duration. Search reports a query-embedding failure that Palace shows left nothing performed by its own code (stage `embedding`, effect `none`): `provider-throttled` with a numeric `ConsumerError.retry_after`, or `deadline-exceeded`, `cancelled`, `cancellation-failed` or `pacer-refused`; an ambiguous throttle and every other query-embedding failure stay `callback-failed`. Pace every embedder you create with one Palace request pacer, queries first. Biblios adds no limiter and no retry of its own, and Palace's reference pacer limits requests and UTF-8 request bytes in one process; it enforces no token quota.

Keep a borrowed namespace handle open and unsealed until `active_work` is zero. Closing the facade refuses while synchronous work, including a waiting writer, is active. Caller-held coordinator critical sections, reentrant writes from callbacks and raw directory writers are outside this concurrency promise. Cancellation is cooperative and cannot terminate a blocked callback. Writer admission checks cancellation and deadlines before waiting; the bounded Palace admission wait itself does not observe them until it returns. After an interrupted publication, inspect durable status and reconcile the original operation; completed vector evidence can permit finishing without repeating providers, while incomplete or mismatched evidence requires recovery. A hard crash after exchanging a previously admitted mirror but before the Palace commit keeps the prior mirror under its retained name; retrying the original operation resumes publication, and this is not a multi-store crash-atomic publication protocol.

The filename section must chunk as the final row; if the mirror's text ends inside an open block that absorbs it, the entry stays pending `name-section-unprojectable` and keeps what it had accepted. A user's own section headed `Filename` earlier in the text is content. For a nominated duplicate, rows whose complete ordered inputs equal the donor's are reused, the filename row included when both names are the same; any differing row is embedded fresh. Body vectors are composed in the destination's own plan order and committed as independent rows. Deleting the donor cannot delete or invalidate the destination. Palace's recorded input digests attest to the submitted-input claim; they do not prove an external provider's behavior.

`bring_current` itself removes obsolete index members and advances the watermark as entries settle; there is no separate finishing call. `bound.checkpoint()` remains the separate writer operation that prepares a read-only mount. Injected progress reports count completed embedding rows; rows for the converting stage and for per-entry outcomes carry `done` and `total` as None, so a consumer must not assume every row has counts; observers describe committed local effects and never imply external publication. The complete runnable local-provider example is `examples/consumer_binding.py`.

## Search and observe completion

`BoundShelf.search` and `open_bound_stack` accept explicitly supplied providers. Only admitted supplied shelves participate; Palace performs one union fusion/rerank for a stack. Provider, storage or reranking failures produce a typed error rather than a degraded accepted answer. Known unbuilt and lagging shelves remain visible in status. Current-hit checks preserve live entry/content/mirror identities: each returned hit is proven against its entry's current accepted record when the answer is assembled, so an entry renamed, replaced, deleted or newly indexed while the query embeds is judged exactly as a search issued after that change would judge it. Only a change of the shelf's epoch, lineage, database generation or embedder and vector selectors during the provider call refuses the answer (`stale-view`). A result's `revision`, `searchable_revision` and `indexing` fields are observed when the query starts; each hit is checked at assembly, so they are not a revision the whole answer is consistent with.

`CallControl` carries an absolute monotonic deadline and a cooperative cancellation predicate. Checks before and after synchronous callbacks prevent accepted late results. They cannot forcibly terminate arbitrary Python code or undo an already dispatched external operation. Keep the binding and providers alive until the call actually returns.

`Observation` identifies the actual local operation, storage view, revisions and affected entries. A failed observer retains the durable effect and its observation in `ConsumerError`; the caller can inspect status and replay the original request. An unsigned callback delivery is not authenticated consumer publication. `ConsumerError` exposes a fixed code, stage, effect and optional observation; provider exception text is discarded. Effects distinguish no effect, namespace commit, derived commit, recovery required and uncertain outcome.

## Opt in to exact vector acceleration and monitor memory

A long-lived process may build one `VectorAcceleration(budget_bytes=..., on_unavailable="refuse" | "fallback", authorize=...)` and pass it as `acceleration=` to `BoundShelf.search` or `BoundStack.search`. It owns one process-wide Palace 0.7 exact in-memory vector cache shared by every thread; build exactly one per process, because the byte budget belongs to that object and it serves only the shelves Biblios searches. `on_unavailable` has no default. Without an acceleration object a search runs exactly the released exhaustive search, reports `vector_routes=None`, and loads neither Palace's cache nor its feed module. Nothing in Biblios turns acceleration on, and no default changed.

A shelf is served from memory only after its index opts into Palace's vector change feed: `bound.enable_vector_feed()` on a read-write binding, through the shelf's one writer (the Palace writer lock every Biblios and Palace writer takes, so it refuses with `writer-busy` while another writer holds it). Every later index write records into the feed. A repeated enable keeps the existing lineage; `enable_vector_feed(new_lineage=True)` starts a new one from the store as it is and is the explicit remedy for a diverged feed. `disable_vector_feed()` drops it. A rebuilt or recovered index has no feed until it is enabled again. A feed write changes the index database like any other index write: run the writer's `checkpoint()` afterwards before read-only bindings can admit the shelf again. A shelf with no index database refuses with `index-unbuilt`; a failed feed write has effect `none` (Palace rolls it back), and a committed write whose read-back failed has effect `derived-committed`.

Every accelerated search returns the same hits, order, scores and per-hit evidence as the exact search. Since Palace 0.7.1 both searches order equal vector distances by chunk id, so tied results are deterministic, and the cache answers ties from memory. `vector_routes` reports, per searched shelf in Palace's order, how its vector legs were answered: `cached_legs` from memory; `oracle_legs` by the released SQL because the cache could not certify parity, for example a vector outside the numeric range its error bound is proved for (exact, not a fallback); `fallback_legs` by the released SQL because the cache was unavailable under `on_unavailable="fallback"`; `reasons`, the reasons for oracle legs (`missing-vector`, `relocated`, `knn-limit`, `non-finite-query`, `numeric-range`) and fallback legs together, so read `fallback_legs`, not `reasons`, to detect a fallback; `bypassed` when the shelf had no local vector leg; and `snapshot_seq`, the feed position read. An accelerated search that searched nothing reports `()`, and an unbuilt stack member has no route. Two behaviours differ from the exact search. An accelerated single-shelf search holds its index snapshot through the rerank, as a stack search always does, so a concurrent excision, checkpoint or settle that must switch the journal mode is more likely to wait or report its documented failure. The first search of a cold shelf loads its vectors inside the call, and neither the call's deadline nor its cancellation interrupts that load; call `acceleration.warm(bound)` ahead of time instead; it returns whether the shelf is now resident, and `False` for an unbuilt shelf.

Only operational unavailability honours `on_unavailable`: `feed-disabled` (enable the feed), `budget` (raise the budget or evict), and the transient `queue-full` and `snapshot`, which are safe to retry. `snapshot` also follows routine events on a resident shelf: a new lineage, a feed pruned past the resident position (for example after a large bring-current), an eviction during a search or a discarded concurrent load; the next search reloads. Under `refuse` the search fails with `vector-cache-<reason>`; under `fallback` it answers exactly and the route says so. A failed accelerated stack search names the code, not the member; per-member `vector_status`, `warm` or single-shelf search locates it. Integrity and access never fall back. A diverged feed (a chunk written outside the feed) fails with `vector-feed-diverged`, malformed feed state with `vector-feed-malformed`, and any other failure inside the cache (a vector of the wrong width, a load or refresh that does not reconcile with the stored count, a store read error inside the cache) with `vector-cache-integrity`; each also evicts the shelf from memory. The integrity code means the cache could not serve a consistent copy, not by itself that the store is corrupt; a store lock wait during a load stays `search-failed`, as it would for the exact search. `vector_status().diverged` is the authoritative divergence check.

`authorize` is the consumer's own protection around the shelf; Biblios supplies no authorization of its own. It receives each searched shelf's admitted `ShelfView` on every accelerated search, hits included, and on `warm`. A false result or an exception fails the search with `vector-cache-unauthorized` and evicts the shelf for every caller, so in-flight searches by other callers may then report `snapshot`: it is a store-level revocation, not a per-caller check. Independently of the hook, the cache serves only the shelves admitted by the current call.

Monitor three scopes, never mixed. `bound.vector_status()` is the store: read in constant work from the feed state, it reports `feed` (`enabled`, `disabled` or `absent`), `vector_rows` (stored vectors), `live_chunks`, `chunks_without_vector`, `epoch`, `last_seq`, `floor_seq`, `feed_entries` and `diverged`; every figure is `None`, never zero, unless the feed is enabled. `acceleration.stats()` is this process's cache, from one snapshot of Palace's allocation ledger: `budget_bytes`, `owned_bytes` (live + retired + pooled + load + scratch), `headroom_bytes`, each category, `leases`, cumulative `counters` keyed by event and reason (for example `loads`, `fallbacks.budget`, `refusals.feed-disabled`, `evictions.authorization`), and per resident shelf its `live_rows`, `dead_rows`, `applied_seq`, `owned_bytes`, loader route and load time. These bytes are the cache's own accounting, an estimate of its allocations, not of the process. `stats().process_peak_rss_bytes` is the operating system's lifetime peak resident set for the whole process, or `None`. Resident `live_rows` equals stored `vector_rows` only at the same feed position. No figure carries text, chunk ids or queries.

`acceleration.evict(bound)` unpublishes a shelf's resident copy at once and works on a closed binding, including the one an excision retired. When its last search ends Palace zero-fills its blocks and keeps them pooled for reuse: `live_bytes` falls and `pooled_bytes` rises, while `owned_bytes`, `headroom_bytes` and process memory fall only when Palace drops pooled blocks under later budget pressure. An excised entry is never served, because each search applies the feed first, but its vector stays in process memory until its block is compacted or the shelf is evicted; evict after an excision whose removal must leave memory. Closing a binding leaves its shelf resident. After an excision the feed keeps only the removed chunks' ids, with cleared payloads, until it is pruned. The cache is exact search only and per process: no memory mapping, approximate index or sharing between processes. Measure memory and latency on the intended corpus and host before making acceleration a service default.

## Ask for one result per source

Pass `distinct=DistinctSources()` to `BoundShelf.search` or `BoundStack.search` to receive at most `limit` results with one result per source; `limit` then counts sources, not chunks. By default each entry is one source (`"<shelf_id>/<entry_id>"`). Supply `DistinctSources(key)` to choose your own source identity and accepted-version rule: `key` receives a `SourceCandidate` (its `shelf_id`, its `entry` and the accepted `stage` it would be served from) and returns the source key as a string, or `None` to reject the candidate, for example a version your application does not accept. A key may name the same source on several shelves of a stack; the best-ranked eligible member is kept, and each shelf's own checks decide its members.

Selection walks the candidates Palace already ranked, in rerank order, after Palace's read snapshot has closed: the same candidates, the same single rerank call and the same provider budget as an ordinary search. The pool is that search's candidate depth (`max(limit, 20)` chunks per shelf), so a pool with fewer distinct eligible sources than `limit` returns fewer; this is normal, nothing is fetched again, and the result's `distinct` says so. To draw from a deeper pool, pass a larger `limit` and keep the first results you need; that also sends more candidates to the single rerank call and can verify more entries. Your key is called once for each walked candidate whose entry Biblios has served (its accepted record, stage and mirror), duplicates included, before the candidate's own chunk is checked; keep it fast and free of side effects. A candidate is selected only if your key accepts it, its source has not been selected yet, and its chunk passes Biblios's checks (its accepted row, membership path and stored evidence), so a stale or rejected top candidate never takes its source's place and the next valid candidate of that source can. A candidate of a source already selected is skipped without further checks.

Every selected hit is re-read when the answer is assembled: a deleted entry is withheld as `not-live`; an index commit since selection as `commit-during-read` (`commit-in-flight` while one is in progress); replaced content as `not-accepted`; a mirror that is no longer the accepted bytes as `mirror-changed`; a renamed entry is served under its new path. A withheld hit is reported in `withheld`, under the reason found at assembly even when an earlier candidate of the same entry was withheld during the walk, and is not replaced. Your key's verdict stands as of selection: it is not asked again at assembly, and an entry's metadata is not re-read, so a key that reads tags or the path decides on the entry as it was when selected. `distinct` (`DistinctReport`) is present whenever you asked for it, including on an unbuilt shelf: `pool` and `walked` count the ranked candidates available and examined, `ineligible` those refused by Biblios's checks or your key, `duplicates` those of an already selected source, `selected` the sources chosen, `returned` the results in the answer (fewer than `selected` when a hit was withheld at assembly), and `underfilled` is true when `returned` is below `limit`. The key, yours or the default, runs behind the same fence as every supplied callback: the call's deadline and cancellation are checked around each call, and a key that raises or returns anything but a string or `None` fails the search with `callback-failed`. A `distinct` value that is not a `DistinctSources` fails with `distinct-invalid` before any provider call. Selection does more local work than an ordinary search: every walked candidate's entry is verified (its mirror read and hashed once per entry), up to the whole pool when the search underfills, on every shelf of a stack; `withheld` and, on a writable binding, the read observations it marks can therefore name entries an ordinary search of the same `limit` would not have reached. Without `distinct`, search is unchanged and `distinct` is `None`. The option composes with `acceleration=` and returns the same answer either way.

## Retain, inspect and excise

Use `retained()`, `read_retained(reference)`, `snapshot(id)` and `history_inventory()` through the bound coordinator. References bind exact content to the namespace/store/epoch and finite currently retained membership. Historical owner fields describe the captured occurrence; a later snapshot or operation may retain the same exact content. A reference is not unrestricted CAS access. Replaced and deleted bytes remain historical; they do not become current search hits.

Excision is explicit and forward-only. `preview_excision` uses Castle's complete content/entry/metadata/operation/snapshot closure. Supply a finite `ExcisionRequest`, explicit snapshot actions and an absent successor root within the declared domain. Accept the exact returned request; an incomplete shared-content selection refuses. Clearing only metadata preserves surviving bytes as metadata-free entries; Biblios does not invent replacement metadata or convert/search those entries.

`excise` coordinates Castle retirement with derived mirror/index/checkpoint disposition. It invalidates the old facade and removes selected derived rows, mirrors, free-page disclosures and old-epoch conversion/scratch records while retaining unselected rows and bytes. Biblios removes every selected entry id and content id from its own records: recorded call results drop the excised entries and a replay of such an operation returns `redacted=True` (its operation id and request digest stay, so a changed request under that id is still refused); curation and cancellation records naming the selection are removed; an unselected entry's record of a selected source forgets that source; kept retention records forget a selected source; and the completed disposition marker keeps only the operation id, request digest, counts and the residue it reported. `residue` reports `biblios.identifier-files`, the count of Biblios files under the palace and mirror roots that still contain a selected identifier in any form; it is expected to be zero, and a caller that relies on the removal checks it. The result supplies a successor binding with `service_resumed=False`. Explicitly reconcile your own publication/resumption policy before opening that successor; a library result cannot assert that policy was satisfied.

An interrupted cutover leaves the library's pending disposition marker and actual Castle recovery records. `recover_excision(binding, session, original_request)` accepts only the original roots, request digest and operation ID, resumes Castle's supported recovery, and completes idempotent derived cleanup. It never falls back to the predecessor. Unfinished cleanup blocks admission, including a newly opened successor. This covers Biblios-managed derived artifacts, not provider backups, independently copied documents, application logs or consumer-controlled publication history.

## Storage and release limits

The caller owns storage/mount/ancestor custody and must preserve Castle's filesystem protection requirements. A shared filesystem that changes immutable object modes is not qualified merely because a local temporary directory works. Read-only mount qualification and installed-artifact qualification establish different properties. Keep originals and exercise a disposable shelf before adopting a changed experimental version.

The CLI remains a thin interface over its existing operations; consumer excision is a library call, not a new command. MCP, vector caches shared between processes, new security mechanisms and unrestricted privileged execution are outside this contract. Source delivery does not publish a new version or certify a consumer application's behavior.
