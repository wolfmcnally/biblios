# Biblios 0.7.2 release preparation

Version 0.7.2 is the next experimental release at the existing [GitHub repository](https://github.com/wolfmcnally/biblios), a patch release after the published experimental 0.7.1. As directed by the operator on 2026-11-24, it moves the Palace dependency to the published v0.8.2, whose Bedrock embedding selector accepts the US geographic inference profile and uses it when the model is omitted. It changes no Biblios code, interface, CLI command or storage format; existing shelves keep their recorded embedding. Publication follows artifact installation checks and the final exact-tree gate. This preparation record does not itself claim publication.

## Intended artifacts

The version tag is `v0.7.2`; there is no `v0.4.0` tag. The attached package artifacts are `biblios-0.7.2-py3-none-any.whl`, `biblios-0.7.2.tar.gz` and their SHA-256 checksums. No PyPI upload, hosted documentation, model weights, OCR executable, private configuration or user corpus is included. The wheel and source distribution carry the same declared dependencies. Published substrate releases are selected by tag; the lockfile retains their exact resolved commits. A tag alone does not establish that an upstream release was published.

Python support remains 3.12 and 3.13; the managed checkout runtime is Python 3.12. Git and uv fetch public prerequisites. macOS and Linux have development qualification; Windows is unqualified. See [installation](project/README.md) and [update/uninstall guidance](project/RELEASE.md).

## Changes in 0.7.2

Dependencies: Palace v0.8.2 (from v0.8.1), tag peeled to caf55a93e7331034acb8ff95e8f4f8fbdc8ea6e2; its hosted CI passed on that commit, and its release wheel and source distribution match their published checksums. Palace 0.8.2's Bedrock selector accepts exactly the direct model `cohere.embed-v4:0` and the US geographic inference profile `us.cohere.embed-v4:0`; `model` is now optional and an omitted model selects the US profile, which Palace accepts only with region us-east-1, us-east-2, us-west-1 or us-west-2. Every other model or profile is refused. The selected model is part of the embedding identity, so direct and US-profile stores never share an identity or vectors. Only Palace's selector validation changed.

Biblios's code is unchanged: it hands the composed `palace` section to Palace, records the selector Palace resolves when a shelf is created, and afterwards reads only that record. A shelf created with an explicit `cohere.embed-v4:0` stays on the direct model whatever later settings say. New Bedrock settings that omit `model` create shelves on the US profile, which a direct shelf cannot share a stack with. Two proofs are added: one checks that the model choice survives a layered composition and that Palace's refusals pass through; the other checks that direct and US-profile shelves keep distinct identities and are never stacked, and that an existing direct shelf's selector is left unchanged. The getting-started chapter documents the model choice and how to move routes. No live Bedrock call was made for this release; the US-profile route is not established against AWS.

The repository's AWS qualification settings pin the direct model and are unchanged; that tooling's retention-check expectation is as described for 0.7.1.

Limits: as for 0.7.1. Only macOS ARM64 ran this release's checks and clean installation; Biblios has no hosted CI, and no Linux or Linux ARM64 qualification is claimed.

## Changes in 0.7.0

A consumer can pass `distinct=DistinctSources(key)` to bound single-shelf or stack search to receive at most `limit` results, one per source. The key receives a served candidate (shelf, entry, accepted stage) and returns the source key or `None` to reject it; by default each entry is one source. Palace v0.8.0 walks its already ranked candidates after its snapshot closes and asks Biblios for each key: a candidate counts only after Biblios's own checks serve it and the key accepts it, so a stale or rejected top candidate never hides a valid sibling. The candidates, the single rerank call and the provider budget are those of an ordinary search; a short pool returns fewer results and `DistinctReport` says so. Every selected hit is re-read at assembly (deleted, replaced, renamed, re-indexed, or its mirror edited since selection) and a withheld hit is not refilled. The key runs behind the standard callback fence. Without the option nothing changes, except that the CLI's JSON search output, which prints the result's fields, gains a `"distinct": null` key, as it gained `vector_routes` in 0.6.0.

Dependencies: Palace v0.8.0 (from v0.7.1), tag peeled to 2f96c7d390fd1bf24098e884f70d68e4a57d78e8; its release wheel and source distribution match their published checksums.

Interface changes: `DistinctSources`, `SourceCandidate`, `DistinctReport`; the `distinct` keyword of `BoundShelf.search` and `BoundStack.search`; `SearchResult.distinct` and `StackResult.distinct`.

One independent plan review and one independent code review (Fable High) ran on this candidate, after a preparation with its own independent plan and code advice. The plan review's eleven findings were disposed before implementation; the code review found nothing critical, high or medium, and its three low findings were adopted with new proofs. Twenty-seven proofs are each red-witnessed. The corrections made after the code review were not independently re-reviewed.

Limits: the candidate pool is fixed at the ordinary search depth, so underfill is normal; only macOS ARM64 ran this release's checks; all proofs are synthetic and offline.

## Changes in 0.6.0

A long-lived consumer can opt shelves into Palace v0.7.0's exact in-memory vector cache. It builds one `VectorAcceleration` per process with a byte budget and an explicit choice, with no default, of whether operational unavailability refuses or falls back, and passes it to bound single-shelf or stack search. A shelf is served from memory only after `BoundShelf.enable_vector_feed()` opts its index into Palace's vector change feed through the shelf's one writer. Accelerated searches return the same hits, order, scores and per-hit evidence as the exhaustive search, and `vector_routes` reports per shelf whether its vector legs came from memory, from the exact SQL because parity could not be certified, or from a visible fallback. Only `feed-disabled`, `budget`, `queue-full` and `snapshot` can fall back; a diverged or malformed feed, any other failure inside the cache and an authorization refusal fail with their own codes under either setting. An optional consumer hook receives each searched shelf's admitted view; the cache serves only the shelves the current call admitted. Monitoring keeps three scopes apart: `vector_status()` reports the store's vector and chunk counts from the feed state (`None`, never zero, when unknown); `stats()` reports the cache's budget, owned bytes by category, headroom, counters and per-shelf resident rows from Palace's own accounting; `process_peak_rss_bytes` is the operating system's peak for the process. Without an acceleration object nothing changes and neither Palace's cache nor its feed module is loaded. Stack search now calls Palace's prepare and execute steps directly, which Palace documents as the same operation as its one-shot search.

`biblios.__version__` is read from the installed package metadata, so importing Biblios needs its installed distribution; 0.5.0 reported `0.4.0`.

Dependencies: Palace v0.7.0 (from v0.6.0), tag peeled to 472e76f0f3a96430a45b60ae0d4dec57fc6872ed; its release wheel and source distribution match their published checksums.

Interface changes: `VectorAcceleration`, `StoredVectors`, `VectorRoute`, `ResidentShelf`, `AccelerationStats`; `BoundShelf.vector_status`, `enable_vector_feed`, `disable_vector_feed`; the `acceleration` keyword of `BoundShelf.search` and `BoundStack.search`; `SearchResult.vector_routes` and `StackResult.vector_routes`; the codes `vector-cache-feed-disabled`, `vector-cache-budget`, `vector-cache-queue-full`, `vector-cache-snapshot`, `vector-cache-unauthorized`, `vector-cache-integrity`, `vector-feed-diverged`, `vector-feed-malformed`, `vector-feed-failed` and `index-unbuilt`.

One independent plan review and one independent code review (Fable High) ran. The plan review's ten findings were disposed before implementation; three owner questions were answered within the relayed scope, and the tag and publication remain the operator's. The code review found nothing critical or high; its four medium findings (classification at the edges of the integrity rule, warming an unbuilt shelf, the documented memory effect of eviction, and unproven malformed-feed and stack error paths) and its lower documentation and test-oracle findings were adopted, each correction verified by fresh tests and twenty red-witnessed proofs. The corrections made after the code review were not independently re-reviewed.

Limits: exact search only, one cache per process and no sharing between processes; an accelerated single-shelf search holds its index snapshot through the rerank, as stack search already did; a cold shelf's first load is not interrupted by the call's deadline or cancellation (warm it first); an excised vector stays in process memory until compaction or eviction, although it is never served; cache byte figures are the cache's estimate, not the process's footprint. All proofs are synthetic and offline. Only macOS ARM64 ran this release's checks and clean installation; Biblios has no hosted CI, and no Linux or Linux ARM64 qualification is claimed for 0.6.0. No latency, memory sizing or corpus-scale measurement qualifies it; making acceleration a service default is the consumer's decision after its own measurement.

## Changes in 0.5.0

A provider throttle is now a typed signal that never hides an uncertain attempt, and a document whose only failure was a definite throttle goes back to the caller as not done, nothing committed, try later. Palace v0.6.0 raises a typed provider failure that records, over every attempt, whether the provider may have performed the work; honours the provider's retry hint as a floor with jittered backoff, ending at once when the hint exceeds the permitted wait or the caller's deadline; paces every physical request through an injected request pacer; and bounds pacer waits, backoff and new attempts by a deadline and cancellation scope. See [provider throttling](briefs/provider-throttling.md).

Biblios classifies an entry's provider failures once, after every slice it submitted has returned: `pending` with effect `none` only when every failure left nothing performed and was a throttle, deadline, cancellation or pacer refusal, otherwise `uncertain`, with the code `provider-throttled` whenever the provider throttled. Once a call observes a throttle it admits no further entry and sends no further slice; submitted work drains, a fully answered entry still commits and the rest stays marked. Recorded results keep exactly their earlier shape: `BringCurrentResult.throttled` is computed from the recorded codes, and the call-local `BringCurrentResult.local` (retry hint, failed invocations, discarded answers and Palace's usage summary) is never recorded, so a replay never renews a retry hint. Search reports a definite query-embedding throttle as `provider-throttled` with a numeric `ConsumerError.retry_after`. Pooled provider calls run in a copy of the caller's context, and `bring_current` and search carry their deadline and cancellation into Palace.

Dependencies: Palace v0.6.0 (from v0.5.1).

Interface changes: `ConsumerError.retry_after`; `BringCurrentResult.throttled` and `BringCurrentResult.local` with the new `CallLocal`; the codes `provider-throttled` and, from Palace's own stops, `pacer-refused`; a definite throttle, deadline, cancellation or pacer refusal is now `pending` rather than `uncertain`; other provider failures remain `uncertain`. `provider_calls` counts embed invocations that returned, when each returns; before, a returned answer that failed the following control check, or was drained after its entry had failed, was not counted.

One independent code review (Astra) ran on the code candidate, with re-reviews. It found five defects, each reproduced and then fixed with a failing-first witness: an answer float32 cannot hold could leave an entry looking complete, so it was reported twice and handed to the caller's authority; an invalid answer drained after a throttle was not checked; answers of an entry refused before its stage was persisted were not counted as discarded; the guide misstated which search codes are reported; and a malformed answer could raise out of the whole call. The final re-review found no unresolved code findings; a last pass over the whole candidate found one overstated sentence in these release records, which was corrected. The documentation and test-governance records were otherwise not independently reviewed.

Limits: no live provider throttle run qualified this release; Palace's reference pacer counts requests and UTF-8 request bytes in one process and enforces no token quota; there is no guaranteed total call duration: Palace's per-operation transport timeouts do not bound a response that keeps arriving in pieces or SDK credential resolution, and Biblios drains every submitted call before returning.

## Included from 0.4.0

Version 0.4.0 was prepared but never tagged; its changes, described against 0.3.2, ship in 0.5.0.

Castle is the only authority for an entry's name, path and attributes; a mirror is content. Mirrors Biblios writes carry no filename or path: the default converter stages the source under a neutral name and title, and a supplied renderer receives no name. The index adds the current Castle filename after the mirror's bytes as its own final row, so a rename re-embeds only that row and never touches the mirror, closing the case where a rename left the old filename readable on disk. A mirror's front-matter header is never an authority: values under Castle-controlled keys are ignored, and other scalar fields that are not declared converter provenance are searchable as an attributed `Mirror metadata` row. Headers are no longer validated, so a malformed header never isolates an entry. No change was needed in Palace, Castle or Drawbridge. See [metadata authority](briefs/metadata-authority.md).

Dependencies: Palace v0.5.1 (from v0.5.0), which treats an unloadable front-matter header as malformed; PyYAML is declared directly.

Interface changes: `renderer(result) -> MirrorDocument(markdown)`; `ConversionRequest` without a display name; `DerivationPolicy.provenance_header_fields` in place of `required_header_fields`; the isolation classes `mirror-header-invalid` and `mirror-name-section-invalid` are gone. `EntryMetadata.display_name` and `SetEntryMetadata.display_name` are removed, so Castle's namespace name is the only name.

Earlier releases were developer previews with no shelves to carry: a shelf written by 0.3.x is not supported (reading its entries fails) and is rebuilt from its originals.

One independent code review (Fable) ran. Its findings were addressed before release with failing-first witnesses: Drawbridge's per-format header fields would have been indexed as attributed metadata; Castle-controlled keys matched only in lower case; Biblios recognised front matter differently from Palace; a filename beginning with `#` could never be indexed; date values and non-ASCII keys were dropped; and PyYAML is now a declared dependency. Stale documentation it found was corrected. The post-review changes were not re-reviewed. Two proofs under the owner's named witness exception changed content to the new behaviour without governance records, because the exception forbids modifying or retiring them; one still carries a name from the earlier limitation, explained in its docstring.

## Included from 0.3.2

A lost derived store can be rebuilt while the user's mirrors survive. Before, after the palace store was removed, every surviving mirror read as user-owned and no call could index it again without deleting or rewriting the user's file. `grant_first_ingestion` now takes an optional `expected_mirror_sha256`: the existing file is adopted as the entry's mirror only if its bytes hash to exactly that caller-vouched digest, and the next `bring_current` indexes those bytes without conversion or any write. A mismatched digest refuses `mirror-user-owned`, an absent file `mirror-missing`, and a mirror edited between the grant and indexing is isolated, never adopted. The grant stays bound to the entry's current content, the operation id and write-grade creation admission.

Adoption still runs the caller's write-grade `authorize_creation`, which sees the grant kind `adopt-existing` and may refuse it with the mirror untouched. Granting again with a new digest, after the user edits the file, replaces the vouched digest. Each adoption is consumed once its entry is accepted; a second grant for the same entry refuses `converted-before`. The rebuild proof checks that no mirror is renamed, retained or rewritten.

One independent code review ran on this correction. Its findings on re-vouching, the missing proofs of creation admission and grant consumption, and the strength of the no-write proof were addressed afterward with failing-first witnesses; two smaller findings, an unintended change to the ordinary grant fingerprint and an uncontained grant-time file read, were fixed without a dedicated witness. Those changes were not reviewed again. Two findings are documented rather than changed. An adopted mirror is treated wholly as user content, so the rebuilt index adds its own filename section and the renderer's original name section stays as body text; the rebuilt index is therefore not identical to the lost one. And excising an adopted entry's source keeps its mirror in place and reports it as kept, as for any user-edited mirror.

## Included from 0.3.1

Excision now leaves no selected entry id or content id (prefixed or bare sha256) in Biblios's own records. Recorded call results drop the excised entries; replaying such an operation returns `redacted=True`, and its operation id and request digest stay, so a changed request under that id is still refused. Curation and cancellation records that name the selection are removed, an unselected entry's record of a selected earlier source forgets that source, and kept retention records forget it too; the completed disposition marker keeps only the operation id, request digest, counts and the residue it reported. A final bounded byte scan of the palace and mirror roots is reported as `biblios.identifier-files` in the residue; it is expected to be zero, and a caller relying on the removal should check it. The release's proofs also scan the successor's Castle roots and find none.

A search is no longer refused `stale-view` because another entry was curated or indexed while the query embedded. Each returned hit is proven against its entry's current accepted record, so an entry renamed, replaced, deleted or newly indexed mid-query is judged exactly as a search issued after the change would judge it; only a change of the shelf's epoch, lineage, database generation or embedder and vector selectors refuses the answer. The adoption guide also drops two stale references (`pipeline.finish`, `pipeline.status`) and states that progress rows for conversion and per-entry outcomes carry no counts.

The persistent edit observer planned for this line is not part of 0.3.1; it remains in development.

## Included from 0.3.0


One indexing core now serves the library, CLI and bound entry points; the separate conversion and reconciliation modules are gone. Each entry is authorized, staged and promoted on its own, so a slow or failed document no longer holds back the others, a crash at any stage boundary never serves unauthenticated state or re-embeds, and replayed calls return their recorded result. Castle v0.4.0's touched-record admission keeps per-entry work flat as a shelf grows (counted at 20, 60 and 200 entries).

Mirrors belong to the user once created. Reconcile re-indexes an edited mirror without converting over it; replacing a file is a new ingestion that converts the new bytes and keeps the previous mirror under a retained name; a damaged mirror isolates only its entry. A copy receives one first mirror converted from its source, and the new `grant` command gives a never-converted entry its first mirror explicitly. `reconcile --entry` and `--sweep` bring edited mirrors current.

Search checks every hit through Palace v0.5.0's per-hit evidence: a hit whose stored body, input digest or vector differs from the entry's accepted record is withheld, and only that entry is affected. Delete stays logical: the entry leaves search at once, its index rows leave at the next reconcile and its bytes stay in Castle; delete is not reversible, and restoring from backup is the way back. Excise, meant for cleaning up information spills, now merges the full-text index's segments before vacuuming, so no excised word survives in any Biblios-managed index, journal or free page; it makes no claim about storage-layer copies, backups, sync, provider-side copies or operating-system temporary files.

Status, search and diagnosis read a shelf whose first reconcile is still creating its index store as a shelf with no store yet, instead of failing with a raw SQLite error. The packaged examples use the new result types.

A shelf written by 0.2.x is refused until its owner migrates its Castle namespace once, explicitly and with a backup; see [update guidance](project/RELEASE.md). Biblios never migrates it. Drawbridge v0.3.1 and Conric v0.1.0 are unchanged.

## Included from 0.2.1

Public reads and strict search now finish while a document embedding callback is held. Writer admission precedes namespace locking and the reader mutex is released during embedding; stale provider results still refuse publication, competing writers keep one admission order, and active work still protects the shelf lifetime. Conversion, rendering and input preparation remain synchronous. Waiting for writer admission observes cancellation and deadlines only after its existing bounded wait returns. A hard crash after mirror replacement but before index commit may require restoring the previous admitted mirror; no multi-store crash atomicity is claimed. Those 0.2.1 dependencies were the same published releases as 0.2.0.

## Included from 0.2.0

The library adds explicit consumer-controlled shelf binding and read-only use, revision-bound retry, injected conversion and rendering, same-shelf body-vector reuse with independent destination-name embeddings, strict search and publication observations, and coordinated finite retained-content/history/excision access. Destination rows remain independent after donor removal. Excision is an explicit library operation; the CLI still has 22 commands and logical removal retains source bytes. MCP remains held.

The optional Conric `biblios.max_file_bytes` setting is a positive integer and defaults to exactly 104857600 bytes (100 MiB). Consumer create, replace, import and copy use the configured limit when passed the composed settings. Aggregate import/copy admission is at least that per-file limit. Conversion body/mirror, chunk-count, checkpoint and vector-snapshot controls remain separate finite limits; source admission does not promise that every permitted upload fits every processing budget.

Explicit larger finite conversion envelopes and snapshot budgets are supported without changing their defaults, model dimensions, rendering or input identity. Durable checkpoint admission measures encoded UTF-8 JSON bytes against the existing 512 MiB ceiling. Retry preserves uncertain dispatch and committed-but-unaccepted distinctions; increasing a read-only resource budget does not silently change the original semantic request or redispatch conversion.

## Qualification and limits

Release qualification inspects the actual wheel/source archive, installs each into an isolated environment outside the checkout, verifies dependency sources and installed package origin, and exercises synthetic library/CLI behavior. The repository's changed-path selection and final bare full gate bind the final release source. Their exact results and artifact digests belong to the release receipt and GitHub release notes; historical development runs are preserved separately.

The configured per-file limit is tested with small synthetic fixtures. No 100 MiB stress test, full-RAG boundary run, memory benchmark or performance gate is part of this release. The known pinned mdBook/admonish version warning remains separate from successful generated-link, asset, anchor, search and print checks. The 0.2.1 and 0.2.2 guide edits were version, responsiveness and dependency wording only; the 0.3.0 guide edits describe user-owned mirrors, the `grant` command and the new reconcile options, and no new manual browser inspection is claimed for them. Human CLI/library usability judgments remain open.

Two assurance limits are disclosed for 0.3.0 and still apply. The 0.3.1 corrections each have a failing-first witness. Two independent code reviews ran. The first found that the redaction missed three record types; the second found that the generic fix hid part of the residue, missed grant and creation-intent records, read whole files into memory and could act on an unrelated row. The final keyed redesign, a bounded streaming detector and a schema-coverage proof address those findings and have their own witnesses, but they have not been independently reviewed again. One case remains untested: an interruption between the identifier scrub and the final marker write. Recovery repeats the scrub. The project suite passes on macOS; on the Linux lane five read-observation tests that search without a supplied reranker fail because Palace's default reranker model is not provisioned there and network egress is blocked. That limit of the lane predates this release; the tests and the search code they exercise are unchanged. The membership-proof representation and the changes made after the single independent code review this release cycle allowed (the Castle v0.4.0 and Palace v0.5.0 adoption, per-hit verification, spill-grade excision and two concurrency fixes) have had no independent code review; they are covered by the automated suite. And 39 membership proofs in the test suite were admitted without an observed failing run, under the owner's named exception; the repository's test-governance check lists them as unwitnessed until each is witnessed. Upgrading a 0.2.x shelf is proved on synthetic fixtures only; no real 0.2.x shelf was migrated during qualification.

Keep original documents. The API and on-disk formats may change before a stable release. Existing shelf data and configuration are not modified by installing or uninstalling the application. Biblios supplies no encryption, authentication or authorization; surrounding applications own those boundaries. No automatic legacy-shelf conversion or external provider call is implied by installation.
